# Updates

Version 1. How Conduit components learn about, verify and install new
releases.

## Keys

| Key | Type | Signs | Public half lives in |
| --- | --- | --- | --- |
| Release key | ed25519 | daemon (and hub) release payloads | `internal/update.ReleaseKey`, a hub's `CONDUIT_HUB_RELEASE_KEY` |
| Desktop updater key | minisign (Tauri) | desktop bundles | `apps/desktop/src-tauri/tauri.conf.json` |
| Android signing key | Java keystore | the APK | the APK itself (Android checks updates match it) |

Private halves are repository secrets used only by the release workflow:
`CONDUIT_RELEASE_PRIVATE_KEY`, `TAURI_SIGNING_PRIVATE_KEY` (+ `_PASSWORD`),
`ANDROID_KEYSTORE_BASE64` (+ password and alias). Forks set their own and
override the public halves.

## Release payload

```json
{"component":"daemon","channel":"stable","platform":"linux-amd64",
 "version":"0.2.0","url":"https://…/conduitd-linux-amd64",
 "sha256":"<hex>","notes":"…"}
```

A release is `{payload, signature}`: base64 of the exact payload bytes and
an ed25519 signature over them. Verifiers check the signature first, then
that `component` and `platform` are theirs, then the download's SHA-256.

## Feeds

- **Release manifest** (default): `conduitd-release.json`, attached to each
  GitHub release and read from
  `https://github.com/Elchi-dev/conduit/releases/latest/download/conduitd-release.json`.
  Shape: `{"version":"0.2.0","releases":{"linux-amd64":{payload,signature},…}}`.
  `tools/release` builds it from the release binaries.
- **Hub**: `CONDUIT_UPDATE_FEED=hub:https://hub.example.com` makes the
  daemon ask `GET /v1/updates/daemon/{channel}/{platform}?current=…`, which
  answers one signed release or 204. Operators publish with `POST /v1/releases`.

Settings: `CONDUIT_UPDATE_FEED`, `CONDUIT_UPDATE_CHANNEL` (default `stable`),
`CONDUIT_UPDATE_CHECK=off` to stop background checks.

## Daemon self-update

1. A minute after start, then every six hours, the daemon checks the feed.
   A newer verified release raises the `update.available` event; the web app
   and desktop shell show it. Nothing installs without a person.
2. `POST /api/v1/system/update/apply` (owner or admin, signed in) or
   `conduitd update` downloads the binary next to the current one, checks the
   SHA-256, renames the current binary to `conduitd.old`, moves the new one
   into place, writes `update-pending.json` in the data folder, and restarts
   (exec on Unix, keeping the PID for service managers; a new process on
   Windows, which waits for the port).
3. **Probation.** Each start while `update-pending.json` exists counts an
   attempt. A version that serves for a minute is confirmed: the marker and
   `conduitd.old` are removed. On the third start without confirmation the
   daemon restores `conduitd.old` (keeping the bad one as `conduitd.failed`)
   and restarts into it. This relies on a service manager restarting a
   crashed daemon (systemd, launchd, a Windows service, Docker `restart:`).
4. The outcome (`applied`, `confirmed`, `rolled_back`) is kept in
   `update-last.json` and shown in Settings → Updates.

Development builds (version `dev`) and daemons run by the desktop app
(`CONDUIT_MANAGED`) never replace themselves.

## Desktop

The Tauri updater checks `latest.json` (generated by the release workflow
with per-platform URLs and minisign signatures), verifies, installs and
restarts the app; the sidecar daemon updates with it. Windows installs run in
passive mode.

## Android

The APK isn't in a store. The app checks the same GitHub release for a newer
APK and hands it to Android's installer, which refuses it unless it's signed
with the same key (phase 12).
